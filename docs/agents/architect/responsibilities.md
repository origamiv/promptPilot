# Обязанности Architect Agent

## Основные обязанности

1. **Анализ существующей кодовой базы** — изучить текущую архитектуру перед проектированием
2. **ADR** — фиксировать архитектурные решения с обоснованием
3. **API-контракт** — спроектировать все эндпоинты в OpenAPI формате
4. **Схема БД** — спроектировать таблицы, связи, индексы
5. **Документация** — создать понятные артефакты для других агентов

## Definition of Done

Все файлы создаются в `docs/pm/features/{feature_task_id}/`

- [ ] `api-contract.yaml` создан с описанием всех новых эндпоинтов
- [ ] `db-schema.md` описывает все новые/изменённые таблицы
- [ ] `ADR.md` создан если принято нетривиальное решение
- [ ] Все поля запросов/ответов описаны с типами данных
- [ ] Обработка ошибок описана (коды HTTP, структура ошибки)
- [ ] Статус задачи обновлён на `completed`

## Чеклист API-контракта

- [ ] Все эндпоинты используют версионирование `/api/v1/`
- [ ] HTTP-методы соответствуют операциям (GET-чтение, POST-создание, PUT/PATCH-обновление, DELETE-удаление)
- [ ] Структура ответа единообразна во всём API
- [ ] Описаны коды ошибок (400, 401, 403, 404, 422, 500)
- [ ] Пагинация описана для списков
- [ ] Авторизация описана (Bearer token)

## Чеклист схемы БД

- [ ] Таблицы во множественном числе, snake_case
- [ ] Первичные ключи определены
- [ ] Внешние ключи описаны с поведением при удалении
- [ ] Индексы для поиска и JOIN
- [ ] timestamps() на всех таблицах
- [ ] softDeletes() для бизнес-сущностей

## Антипаттерны

- **Не проектировать "на вырост"** — только то что нужно сейчас
- **Не нарушать существующие конвенции** — изучи проект перед проектированием
- **Не оставлять без ADR** нетривиальные решения (нестандартная структура, нарушение REST)
- **Не делать эндпоинты без описания ошибок** — клиент должен знать что ожидать
